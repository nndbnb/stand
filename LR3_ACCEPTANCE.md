# ЛР3 — краткий гайд приёмки (вариант 12)

**Что показываем:** MOEX ISS (TQBR) → локальные `raw/stream`, `raw/history` → SeaweedFS S3 (`raw/`) → очищенные Parquet (`clean/`) → запрос DuckDB. Подробности: [NOTES.md](NOTES.md), [CATALOG.md](CATALOG.md), [SOURCE.md](SOURCE.md).

## 0. Подготовка (из WSL, каталог репозитория)

```bash
cd ~/stand
source .venv/bin/activate
docker compose --profile lab3 up -d
docker compose ps
```

Ожидание: `collector` и `s3` работают; одноразовый `s3-init` мог завершиться успешно. `git status --short` можно показать отдельно, но локальные результаты и конфигурация `data/` не обязаны быть в Git.

## 1. Что именно собирается и куда попадает

```bash
grep -E '^(SOURCE|SOURCE_FILTER|S3|COLLECTOR_LAKE_PREFIX|ENGINE|COMPOSE_FILE)=' .env
docker compose ps collector s3
curl -fsS http://localhost:9101/metrics | grep -E 'collector_events_total|collector_last_success_timestamp_seconds' | head
```

Ожидание: `SOURCE=moex`, фильтр `stock/shares/TQBR`, `S3=seaweedfs`, `COLLECTOR_LAKE_PREFIX=raw`, `ENGINE=duckdb`. Если метрика названа иначе, покажи список `curl -fsS http://localhost:9101/metrics | grep collector | head`; не выдавай устаревшее число за текущий результат.

**Объяснение:** сборщик пишет закрытые `.jsonl.gz` локально и синхронизирует их в S3 под стабильными ключами `raw/stream/dt=YYYY-MM-DD/hour=HH/` и `raw/history/dt=YYYY-MM-DD/`; уже загруженные закрытые файлы не дублируются.

## 2. Сверка raw-файлов с объектным хранилищем

```bash
docker compose run --rm -T --no-deps --entrypoint python \
  collector /app/src/lake_audit.py
```

Ожидание: `RESULT: OK`, `MISSING=0`, `MISMATCHED_SIZE=0`. На контрольном прогоне 02.11.2026: 10 000 локальных и S3-объектов, 1 345 392 898 байт в каждом наборе, `EXTRA=0`. **Сейчас числа могут вырасти**, потому что collector работает. Сверка проверяет размер и ключ, не хеш каждого объекта.

## 3. Очистка и повторяемость

Показать SQL и логику (без перезаписи готовой партиции):

```bash
sed -n '1,180p' jobs/clean.sql
python3 jobs/clean.py --all --dry-run
```

**Объяснение:** для событий UTC-даты D берём исходное сырьё получения D и D+1, отбрасываем неподходящие записи, оставляем `source='moex'`, `BOARDID='TQBR'`, обязательные ключ/время/SECID, удаляем дубли `event_key` с выбором последней записи, пишем один `clean/event_date=D/part-00000.parquet` (Parquet ZSTD, группы 32768). Повторная обработка пишет в тот же ключ, не добавляет новые `part-*`. Текущий день пропускается.

**Важно:** исходный слой не гарантирует непрерывное покрытие всех календарных суток; 23 и 27 октября в прошлом прогоне были доступны без файлов получения D+1, 26 октября — неполные сутки.

## 4. Проверка clean, уникальности и partition pruning

```bash
python3 jobs/verify_clean.py --day 2026-10-19 \
  2>&1 | tee data/duckdb/lr3-acceptance.log
```

Контрольный прогон 02.11.2026:

| Проверка | Результат |
|---|---:|
| Всего событий clean | 7 814 151 |
| Дат-партиций | 14 |
| Событий за 19.10 | 724 665 |
| Уникальных `event_key` за 19.10 | 724 665 |
| Невалидных строк за 19.10 | 0 |
| Чтение без фильтра: файлы / GET / трафик / время | 14 / 247 / 12.7 MiB / 0.201 с |
| Чтение с `event_date=2026-10-19` | 1 / 1 / 3.5 KiB / 0.0137 с |

Время и HTTP-запросы **могут отличаться**. Главное: фильтр по `event_date` отсекает остальные файлы и результат по ключам корректен.

## Короткие ответы преподавателю

- **Почему S3/SeaweedFS?** Слои `raw` и `clean` отделены от локального диска и доступны другим вычислительным движкам через S3 API.
- **Зачем clean?** Фильтрация невалидных событий и дублей, нормализация UTC, колоночный формат Parquet для аналитики.
- **Почему D+1?** Событие с датой D могло быть получено после полуночи UTC.
- **Почему Parquet и партиции?** Колоночное сжатие и чтение только нужного дня вместо всех файлов.
- **Чем доказывается идемпотентность?** Закрытый raw-файл синхронизируется в тот же объектный ключ, а clean-дата перезаписывает фиксированный `part-00000.parquet`; повторный расчёт не должен добавлять копии.
- **Что не утверждаем?** Нет доказательства непрерывной полноты всех суток или сравнительного бенчмарка с масштабом ×1000.
