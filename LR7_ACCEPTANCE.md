## Подготовить стенд

По заданию к переходу должна быть принята основная ЛР6. Если `jobs/sink.py` ещё работает в терминале, завершить его Ctrl+C. Профиль ЛР7 переводит сборщик из `produce` в `record` и останавливает брокер и реестр.

В рабочей копии ЛР6 получи ветку с GitHub и запусти профиль:

```bash
cd ~/stand-lr6 &&
git fetch https://github.com/nndbnb/stand.git lab7 &&
git switch -c lab7 FETCH_HEAD &&
bash scripts/lr7_apply.sh
```

Используется та же рабочая копия с её настройками и накопленной историей. При первом запуске сборка образа Dagster может занять время. После запуска должны быть доступны Dagster на localhost:8082 и ClickHouse. В Dagster открой **Automation → Schedules → lr7_0130_utc**, проверь состояние **Running** и ближайший tick. Если расписание ранее остановили вручную, включи его. Для настоящего планового прогона WSL, Docker и Dagster должны работать в 01:30 UTC (04:30 МСК).

```bash
docker compose exec -T orchestrator python /opt/jobs/lr7.py history
```

Таблица показывает число событий Iceberg по датам. Для строгой проверки истории с начала доступной записи выполни длинную сверку один раз перед защитой. Она читает закрытое сырьё, повторяет отбор ЛР3 и сравнивает ключи событий в обе стороны с учётом кратности.

```bash
set -o pipefail
docker compose exec -T orchestrator python /opt/jobs/lr7.py audit-history | tee data/lr7/history.txt
```

Условия готовности — охват истории не меньше 28 календарных дней, по обработанным суткам `missing=0 excess=0`. Сверь первую дату с началом записи ЛР1. Дни без объектов D+1 помечаются отдельно. Если raw сохранился, а события суток отсутствуют в Iceberg, пересчитай эту дату через Dagster и повтори сверку. Если сам raw отсутствует, сначала проверь архив сборщика. Один раз сохранённый файл с сегодняшними измерениями не заменяет четыре недели истории.

### Пересчитать всю доступную историю через Dagster

В рабочей копии стенда запусти один backfill:

```bash
docker compose exec -T -w /opt/dagster/project orchestrator python -m lr7_backfill
```

Команда выводит даты и причины пропусков, затем передаёт подходящие закрытые партиции заданию lr7_daily. Для предварительного просмотра добавь `--plan`. День D участвует, если есть закрытые файлы raw/stream за D и D+1. Это проверка наличия файлов; полнота исходных данных зависит от истории сборщика. Каждый запуск проходит все пять шагов. Следи за отдельными запусками в Runs по выведенному backfill ID. Для демонстрации расписания и идемпотентности используй пункты 3 и 4.

## 1. Показать агрегат Spark и совпадение с витриной

**На экране.** В Dagster открой **Assets → iceberg_hourly → Partitions**, выбери закрытые торговые сутки с данными. Для первого расчёта материализуй **все пять активов** для этой даты через задание `lr7_daily` (см. пункт 3). Дождись **Success**. В терминале введи ту же дату:

```bash
read -rp 'Дата партиции из Dagster (ГГГГ-ММ-ДД): ' D
docker compose exec -T orchestrator python /opt/jobs/lr7.py compare "$D"
```

**Что показать.** `iceberg_rows` и `mart_rows` — количество строк-групп за сутки. `events` — число исходных снимков. Сверка читает Iceberg через DuckDB и витрину через ClickHouse; сравнивает час, тикер и все три метрики для каждой группы, проверяет уникальность группы. При расхождении команда завершается ошибкой. Для показа выбери день, где обе таблицы непустые.

**Что сказать.** Одна строка — один час UTC и один тикер SECID. Десять снимков одного тикера в одном часу дают events=10, entities=1. entities считает разные пары (BOARDID, SECID); в пределах одного тикера и одной доски получается одна пара. qty_sum складывает QTY снимков. Одну сделку можно увидеть в нескольких снимках, поэтому эту сумму нельзя называть объёмом торгов. В `jobs/aggregate.py` открой `aggregate`: фильтр по времени, groupBy и overwrite с условием на одну дату. В `jobs/lr7.py` открой `publish`: SELECT из базы `lake_ice` (таблица `clean.events_hourly`), сверка промежуточной таблицы, REPLACE PARTITION. Чтобы увидеть сами строки двух источников:

```bash
docker compose exec -T warehouse sh -c 'exec clickhouse-client -u "$CLICKHOUSE_USER" --password "$CLICKHOUSE_PASSWORD" --multiquery --param_day="$1"' sh "$D" <<'SQL'
SELECT event_hour, SECID, events, entities, qty_sum
FROM lake_ice.`clean.events_hourly` WHERE event_date={day:Date}
ORDER BY event_hour, SECID LIMIT 5 FORMAT PrettyCompact;
SELECT event_hour, SECID, events, entities, qty_sum
FROM mart.events_hourly WHERE event_date={day:Date}
ORDER BY event_hour, SECID LIMIT 5 FORMAT PrettyCompact;
SQL
```

## 2. Объяснить план на реальном дне

Переменная D — дата из пункта 1. Запускай вне одновременного пересчёта этой же даты в Dagster.

```bash
docker compose run --rm --service-ports spark /opt/spark/bin/spark-submit \
  /opt/jobs/aggregate.py "$D" --report /home/spark/work/lr7-plan.json --hold 300
```

| Где открыть | На что указать |
|---|---|
| localhost:4040 → SQL → запрос записи → Scan | В formatted-плане **BatchScan** для `lake.clean.events` содержит границы D и D+1. Таблица разбита по `day(event_time)`. Сопоставь фильтр с числом файлов суток и всего снимка в отчёте. |
| SQL → узлы **Exchange** | Прочитай ключи из строки `hashpartitioning(...)`. Обмен собирает части одной группы с разных задач. Отличай обмен для distinct от обмена по часу и SECID и возможного отдельного обмена для записи Iceberg. |
| **Stages** | Покажи конкретные номера стадий записи из отчёта и их Input / Shuffle Read / Shuffle Write. В отчёте они сняты до вспомогательного подсчёта файлов. Общий список UI может включать и вспомогательные запросы. |

В конце появится сообщение «Spark UI открыт ещё 300 с». Во втором терминале WSL можно сразу записать наблюдения в **NOTES.md → ЛР7**:

```bash
cd ~/stand-lr6
python3 scripts/lr7_notes.py data/spark/lr7-plan.json
```

Покажи из NOTES число стадий, байты Input, полные размеры файлов с данными суток и ключи Exchange. Input показывает счётчик Spark; полный размер Parquet-файлов включает и колонки, которые запрос мог пропустить. Это две разные величины.

## 3. Показать расписание и пересчёт за прошедшие трое суток

1. В **Automation → Schedules → lr7_0130_utc → Tick history** открой успешный tick на 01:30 UTC и перейди по его **Run ID**. Покажи дату партиции (предыдущие сутки) и граф пяти зелёных шагов. **Running** на странице расписания означает только включение. До первого успешного tick свидетельство по этому пункту ещё предстоит получить.
2. Выведи даты, которые надо выбрать. Все даты относятся к UTC.

   ```bash
   for i in 3 2 1; do date -u -d "$i days ago" +%F; done
   ```

3. В Dagster открой **Jobs → lr7_daily → Partitions**, выбери эти три даты и запусти **Launch backfill**. В интерфейсе активов тот же выбор доступен через **Materialize partitions** для всех пяти активов. Включи уже материализованные партиции, если интерфейс предлагает их пропустить.
4. В **Runs → Backfills** открой запись. Покажи три даты, три Run ID и итог каждого. Одна дата соответствует одному запуску; запуски на стенде исполняются по очереди. Шаг `clean_parquet` читает закрытые raw-объекты D и D+1. Если их нет, открой ошибку и проверь эти даты в озере.

## 4. Доказать, что повтор не создаёт дублей

**Сразу после первого успешного backfill** сохрани показатели. Проверь, что скрипт напечатал те же три даты, которые выбраны в пункте 3. Если за время показа наступила полночь UTC, используй параметр последней даты выбранной тройки, например `bash scripts/lr7_evidence.sh before 2026-11-22`.

```bash
bash scripts/lr7_evidence.sh before
```

В Dagster запусти **второй backfill ровно для дат из `data/lr7/dates.txt`**, дождись успеха всех трёх. Затем:

```bash
bash scripts/lr7_evidence.sh after
```

**Что показать.** Два разных backfill в журнале и по одной строке на дату в терминале. Снимки `data/lr7/before.jsonl` и `after.jsonl` содержат число строк каждой таблицы, суммы и SHA-256 упорядоченных групп. Сообщение о совпадении появляется после проверки каждой даты. Расхождение выводится через diff. Содержимое сравнимо при одном и том же закрытом входе; поздно прибывшие события могут законно изменить результат.

## 5. Показать качество, реакцию и каталог

| Проверка | Правило | Что увидит преподаватель |
|---|---|---|
| Свежесть MOEX | От последнего event_time суток до полуночи D+1 прошло не больше 6 часов | WARN при превышении или пустом дне, запуск продолжается. Шесть часов — принятый порог для послеторгового перерыва. Это оценка исторических суток на момент их закрытия. |
| Обязательные поля | event_key, event_time, received_at, source, SECID, BOARDID заполнены | Счётчик missing_required, при нарушении шаг quality_checks красный, запуск Failure. |
| Диапазон и источник | Известные QTY и LAST неотрицательны; доска TQBR, источник moex | Счётчик invalid_values; нарушение завершает запуск ошибкой. NULL для необязательных торговых показателей допускается. |

Для контролируемого показа открой **Jobs → lr7_daily → Launchpad**, выбери уже просчитанную дату, оставь все пять активов и задай YAML конфигурации:

```yaml
ops:

      inject_missing: true
```

Нажми **Launch Run**. В красном шаге **quality_checks → Events** покажи `missing_required` (минимум 1) и `negative_control: true`. Проверка добавляет к своему входному SELECT одну строку с NULL event_key. Таблицы остаются пригодными для защиты; проверка выполняется после публикации витрины, поэтому красный статус сам по себе не откатывает публикацию. Обычные запуски выполняются с inject_missing=false. Открой **CATALOG.md → ЛР7** и покажи обе строки таблиц и цепочку активов.

## Дополнительное задание · 2 балла

Используй последнюю закрытую торговую дату D и до 28 суток реальной истории, включая D. Сначала дождись выхода предыдущей команды Spark, чтобы освободился порт 4040.

```bash

  /opt/jobs/aggregate.py "$D" --skew-days 28 --hold 300 --report /home/spark/work/lr7-skew.json
```

1. В отчёте покажи `top.SECID`, его число событий и отношение к среднему по тикеру. Так определяется кандидат на перекос.
2. В localhost:4040 → SQL покажи **SortMergeJoin** на SECID и затем **BroadcastHashJoin**. Авторассылка выключена; второй запрос явно рассылает справочник частот. Контроль сравнивает количество строк и сумму присоединённых частот.
3. В **Stages** открой номера `merge.stage` и `broadcast.stage`. В каждой стадии покажи список задач, длительности и длительность стадии целиком. В первом соединении поле merge_hot_partition указывает номер задачи, в которую попал самый частый тикер; найди её в таблице задач и сопоставь число строк и время с соседними. Запиши результат:

   ```bash
   python3 scripts/lr7_notes.py data/spark/lr7-skew.json
   ```

4. На защите открой таблицу **NOTES.md → ЛР7 → Перекос**. Назови самый частый тикер, сравни медиану и самую долгую задачу, укажи фактическое изменение времени стадии. Если распределение ровное или вариант с рассылкой медленнее, это и есть результат замера. Для утверждения о перекосе нужны заметная концентрация строк и соответствующая длинная задача.
