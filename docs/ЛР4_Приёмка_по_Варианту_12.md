Предварительные условия

Для допуска к ЛР4 предъявить результат приёмки основной части ЛР3. Таблица формируется из очищенных потоковых событий, доступных в S3. Обработанные исторические свечи сохраняются отдельно, поскольку имеют другую схему.

Объём календарной истории определяется фактической доступностью исходного сырья. За 23 и 27 октября в архиве отсутствовали файлы следующих суток, необходимые для повторного закрытия дня по правилам ЛР3.

Пункты задания

1. Конфигурация SQL-движка

В .env используется ENGINE=duckdb. В COMPOSE_FILE добавлен compose.engine-duckdb.yaml. Подключение к Iceberg выполняется через Lakekeeper REST Catalog.

Проверка:
cd ~/stand
grep -E '^(ENGINE|COMPOSE_FILE|CATALOG_URI|CATALOG_WAREHOUSE)=' .env

2. Запуск профиля lab4

Сервисы профиля lab4 запущены. По отчёту WSL от 03.11.2026 проверка Start lab4 containers завершена успешно. Warehouse lake обслуживается каталогом Lakekeeper, объекты хранятся в SeaweedFS.

Проверка:
docker compose --profile lab4 ps

3. Подключение DuckDB и создание таблицы

Настройка DuckDB хранится локально в data/duckdb/init.sql. SQL определения таблицы размещён в jobs/iceberg_create.sql.

Созданы пространство имён lake.clean и таблица lake.clean.events. Начальная схема соответствует событию Avro v1 из 59 полей. Используется скрытое партиционирование PARTITIONED BY (day(event_time)). Партиция определяется по времени события, а не по времени получения.

Проверка:
grep -E 'CREATE SCHEMA|CREATE TABLE|PARTITIONED BY' jobs/iceberg_create.sql

4. Загрузка истории и повторная загрузка периода

Загрузка выполняется jobs/iceberg_load.py и jobs/iceberg_load.sql. Для выбранного периода сначала удаляются его прежние строки, затем вставляются строки из очищенного Parquet. Период задаётся границами времени [start, end). Старые сутки обрабатываются посуточно; последняя доступная дата — последовательностью из 24 часовых интервалов. Фиксация операций выполняется транзакцией DuckDB.

Первоначальный опыт 02.11.2026: 37 интервалов, 14 дат, 7814151 строк, ноль сбоев выполнения. Повторная загрузка доступных данных 03.11.2026 завершилась успешно. Часовые интервалы без событий не создают новых строк; факт одного нового data-файла для каждого из 24 часов требует наличия строк в соответствующем часу.

Проверка:
python3 jobs/iceberg_load.py --all --dry-run

5. SQL-запросы и отсечение файлов

Запрос jobs/iceberg_benchmark.sql выполнен через DuckDB с EXPLAIN ANALYZE. Сравниваются выборки без ограничения времени и с фильтром по одним суткам.

Замер от 02.11.2026:
без предиката — 19 фактически прочитанных файлов, 128 HTTP GET, 20.1 MiB HTTPFS in, 0.288 с;
с предикатом по 19.10.2026 — 2 файла, 7 HTTP GET, 4.1 MiB HTTPFS in, 0.112 с.

Число прочитанных файлов не следует смешивать с количеством всех активных файлов таблицы. Показатель HTTPFS in описывает сетевое чтение конкретного запроса, а не объём таблицы на диске. По отчёту 03.11.2026 проверка запросов завершилась успешно.

Проверка:
docker compose run --rm -T duckdb -init init.sql -bail -f /dev/stdin < jobs/iceberg_benchmark.sql

6. Подключение Spark и перечень снимков

Конфигурация Spark размещена в conf/spark/spark-defaults.conf. Используется Lakekeeper REST Catalog и Iceberg S3FileIO. Диагностические запросы представлены в jobs/maintenance.sql.

Проверка:
docker compose run --rm -T spark /opt/spark/bin/spark-sql -e "SELECT snapshot_id, committed_at, operation FROM lake.clean.events.snapshots ORDER BY committed_at"

История изменений определяется по snapshot_id, времени фиксации и типу операции. Данные таблицы хранятся в Parquet, метаданные — в формате Iceberg.

7. Чтение прошлого снимка и откат

Эксперимент 02.11.2026 проведён через контрольную повторную вставку 510 записей. До вставки таблица содержала 7814151 строку. После — 7814661 строку при 7814151 уникальном event_key. Чтение прежнего снимка через VERSION AS OF вернуло 7814151 строку. Процедура rollback_to_snapshot восстановила прежнее логическое состояние.

Исходный SQL: jobs/iceberg_bad_insert.sql.
Подтверждение: раздел ЛР4 в NOTES.md.

Выполненный затем expire_snapshots сократил сохранённую историю. Прежние идентификаторы снимков используются в документации как данные завершённого эксперимента, а не как доступные сейчас версии.

8. Компакция файлов данных

Перед компакцией в таблице было 20 активных файлов общим размером 764703868 байт. В партиции 27.10.2026 находилось пять файлов общим размером 3459547 байт.

Выполнена процедура rewrite_data_files с параметрами по умолчанию. Пять файлов этой партиции объединены в один файл размером 2571537 байт. После операции таблица содержала 16 активных файлов, количество логических строк не изменилось.

Выбор партиции для переписи определяется сочетанием размеров файлов и условий процедуры. В рассматриваемом запуске наиболее подходящей группой оказались файлы последних доступных суток.

Текущая диагностика без изменения таблицы:
docker compose run --rm -T spark /opt/spark/bin/spark-sql -e "SELECT partition, count(*) AS files, avg(file_size_in_bytes) AS avg_bytes FROM lake.clean.events.files GROUP BY partition ORDER BY partition"

9. Устаревание снимков

Процедура expire_snapshots выполнена 02.11.2026 с сохранением последнего снимка. До операции было 22 снимка, после — один. Число логических строк не изменилось.

Подтверждение количества снимков и результатов выполнения процедуры приведено в NOTES.md. В протоколе исторического опыта приведены значения файлов данных и снимков. Для полного сопоставления числа физических объектов управляемого префикса Iceberg до и после процедуры необходимы отдельные S3-инвентаризации каждого состояния; данные 02.11 по обеим точкам сравнения не фиксировались. Повторный запуск процедуры только ради этой демонстрации не предусматривается.

Проверка текущего состояния:
docker compose run --rm -T spark /opt/spark/bin/spark-sql -e "SELECT count(*) FROM lake.clean.events.snapshots"
python3 jobs/lr34_inventory.py

Важно: категория iceberg_or_other из инвентаризации содержит смешанные объекты bucket и не является точным счётчиком файлов данной таблицы.

10. Эволюция схемы

К таблице добавлено поле версии 2 исходной схемы: NUMTRADES BIGINT. Изменение выполнялось через ALTER TABLE. По данным эксперимента 02.11.2026 активные data-файлы до и после операции не изменились: 16 файлов, 763815858 байт. В старых строках столбец NUMTRADES содержит NULL, COUNT(NUMTRADES)=0; общее количество строк на момент опыта — 7814151.

Проверка:
docker compose run --rm -T spark /opt/spark/bin/spark-sql -e "DESCRIBE TABLE lake.clean.events"
docker compose run --rm -T spark /opt/spark/bin/spark-sql -e "SELECT count(*), count(NUMTRADES) FROM lake.clean.events"

11. Документация и связи сервисов

В NOTES.md отражены измерения SQL-запросов и обслуживание таблицы. В CATALOG.md представлена запись lake.clean.events и раздел «Связи сервисов». Зафиксированы взаимодействия DuckDB и Spark с Lakekeeper и SeaweedFS, использование PostgreSQL для метаданных каталога.

Конфигурация Spark: conf/spark/spark-defaults.conf.
Конфигурация DuckDB: data/duckdb/init.sql.

Критерии основной приёмки

1. Таблица lake.clean.events создана по схеме события и зарегистрирована в каталоге с партиционированием по дню. История загружена из доступного очищенного слоя.
2. DuckDB читает таблицу через каталог; предикат по времени сокращает число прочитанных файлов и объём сетевого чтения.
3. Выполнены чтение прошлого снимка и восстановление состояния после контрольной записи.
4. Выполнены компакция и expire_snapshots; измерения активных файлов и снимков зафиксированы. Для отдельного критерия по физическим S3-объектам приведён порядок текущей инвентаризации.
5. Добавлено поле версии 2 без перезаписи data-файлов. Каталог данных, связи сервисов и конфигурации подключений документированы.
