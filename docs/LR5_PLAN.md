# ЛР5 — план, реализация и проверка

Основание: «Вариант 012.pdf», страницы 10–11; методические указания, страницы 29–30, 34–35. Вариант 12: MOEX TQBR, SeaweedFS, DuckDB, ClickHouse, DataLens. ЛР3 и ЛР4 используются как готовые источники; повторно выполнять их задания не нужно.

## План и реализация

1. Поднять профиль `lab5`, добавив `BI=datalens` и `compose.bi-datalens.yaml`. Готовые Compose-файлы не меняются. Скрипт `scripts/lr5_apply.sh` сохраняет настройки, проверяет конфигурацию и ждёт сервисы.
2. Создать `stg`, `core`, `mart`; читать завершённые UTC-сутки очищенного Parquet функцией ClickHouse `s3`. Заменять партицию, проверять уникальность ключей до публикации: `jobs/warehouse_create.sql`, `jobs/stg_load.sql`.
3. Собрать звезду: факт одного события, измерения бумаги SCD2, даты и доски. Историю получить из `core` по времени события; при неизменных торговых статусах использовать реальную суточную активность. Файлы: `jobs/security_history.sql`, `jobs/mart_load.sql`, `jobs/security_asof.sql`.
4. Посчитать почасовой агрегат MV. Для повторной загрузки агрегат считается MV над загрузочной таблицей фактов, затем публикуются обе партиции. Это учитывает, что `REPLACE PARTITION` сам MV не запускает.
5. Создать в DataLens подключение ClickHouse, три SQL-чарта и дашборд через API. Каждый запрос проверить через `bi-data-api`; повторный запуск использует созданную книгу. Файлы: `jobs/datalens_bootstrap.cjs`, `conf/datalens/ql_column.json`.
6. Решить вопрос о часах суток UTC и бумагах за всю историю тремя путями. Сверить ответы, выполнить три запуска, сохранить профили, планы, время и чтение: `jobs/lr5.py benchmark`.
7. Выполнить дополнительное: до опыта сохранить прогноз ×1000, создать наборы ×1 и ×10 из одних реальных суток с новыми ключами, загрузить отдельные таблицы Iceberg/ClickHouse, выполнить те же замеры, сверить рост всех групп ровно ×10. В `finally` удалить свои тестовые ресурсы. Код: `jobs/lr5.py experiment`.
8. Сверить результаты с критериями. Файл показа — `LR5_ACCEPTANCE.md`; он содержит только шесть основных критериев и один дополнительный. `jobs/lr5_acceptance.py` ничего не загружает и не меняет.

## Запуск в существующем WSL-стенде

Не запускать одновременно очистку ЛР3, загрузку/обслуживание Iceberg или другую загрузку ЛР5. `run.lock` защищает только от второго процесса ЛР5 в том же рабочем каталоге. Сборщик может продолжать писать raw: ЛР5 читает уже опубликованный clean.

```bash
cd ~/stand
bash scripts/lr5_apply.sh
```

Скрипт использует существующие `.env`, `.venv`, `data/duckdb/init.sql`. Не удаляет исходные данные. Первый запуск DataLens может занять несколько минут. По завершении печатает URL дашборда. Вход DataLens: `admin`, пароль стенда `student`; для изменённого пароля перед запуском задать `LR5_BI_PASSWORD`. Проверить внешний вид трёх графиков в браузере.

Скрипт запускает весь конвейер, включая повтор одних суток, проверку, DataLens, полные замеры и дополнительный эксперимент. При неуспехе возвращает ненулевой код и пишет `data/lr5/last_error.json`; не объявляет частичный запуск успешным. Результаты: `data/lr5/results.md`, `data/lr5/results.json`, профили `data/lr5/profiles/`.

Отдельные повторяемые шаги:

```bash
.venv/bin/python jobs/lr5.py load --all
.venv/bin/python jobs/lr5.py verify --repeat-day 2026-10-19
.venv/bin/python jobs/lr5.py dashboard
.venv/bin/python jobs/lr5.py benchmark
.venv/bin/python jobs/lr5.py experiment --day 2026-10-19
```

Для `--day` нужна дата с реальным очищенным Parquet; полный запуск сам выбирает первую имеющуюся дату. Если по всем данным нет реальных изменений даже суточного числа событий, проверка истории сообщит об этом; вымышленные переходы не вставляются.

Загрузка дневной партиции `stg` атомарна. Публикация разных таблиц ClickHouse не является общей транзакцией. При остановке между заменой факта и агрегата нужно повторить `load --all` и `verify`; сверка MV обнаруживает рассогласование. История и факты пересобираются по всему `core`, чтобы исправление старых суток не оставляло неверных ссылок на SCD2.

## Проверка соответствия приёмке

| Критерий | Реализация | Проверка |
|---|---|---|
| 1. Три слоя и назначение | SQL создания, `NOTES.md` | Слои созданы в локальном SQL-тесте; живой стенд — `acceptance 1`. |
| 2. Звезда, ключи, сортировка, партиции, MV | Факт, три измерения, две MV, обоснование в `NOTES.md` | SQL-тесты повторной загрузки и равенства MV/фактов; живой стенд — `acceptance 2`. |
| 3. История и состояние на дату | SCD2 из `core`, полуоткрытые UTC-интервалы, SQL as-of | SQL-тесты границы интервала, исправленной истории и fallback; живой стенд — `acceptance 3`. |
| 4. S3 Parquet, повтор суток, каталог | `s3`, замена партиции, проверка дубликатов, `CATALOG.md` | Реальные Parquet в локальных тестах; транспорт SeaweedFS проверяется на WSL; `acceptance 4`. |
| 5. DataLens | API создания подключения, трёх QL-чартов, дашборда, запросы к `bi-data-api` | Контракты API и идемпотентность протестированы с транспортом-заглушкой. Реальные API и внешний вид — после WSL-запуска; `acceptance 5`. |
| 6. Три пути, вся история, время/чтение | Полный GROUP BY без лимита, три запуска, равенство ответов, snapshot/инвентарь | Parquet/агрегат сверены локально; реальные Iceberg/S3 и времена — после WSL-запуска; `acceptance 6`. |
| 7. Дополнительное | Прогноз до опыта, ×1/×10, новые ключи, отдельные наборы, удаление | Очистка после сбоя проверена тестом; фактические коэффициенты и очистка сервисов — после WSL-запуска; `acceptance 7`. |

Локальные проверки используют искусственные данные и не являются измерениями пользовательского стенда. Здесь нет доступа к WSL, накопленному clean и локальному DataLens. Поэтому сдача всех критериев и дополнительные замеры не отмечены как фактически выполненные до получения `data/lr5/results.json` и проверки графиков.

Локальная среда проверки: DuckDB 1.5.5 (как в Dockerfile стенда), chdb с ClickHouse 26.11.1.1. Целевой Compose использует ClickHouse 26.3.32.14; его сетевые интеграции проверяются при запуске на стенде.

```bash
python -m pip install chdb duckdb==1.5.5 pyarrow
python -m unittest discover -s tests -p 'test_lr5.py' -v
node tests/test_datalens_bootstrap.cjs
```

Контракты API проверены по исходникам `datalens-tech/datalens-auth`, `datalens-us`, `datalens-backend`, `datalens-ui`; поведение MV — по документации ClickHouse. Текущие результаты локальных проверок: `docs/evidence/lr5-local-tests.txt`.
