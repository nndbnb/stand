Пункты задания

1. Конфигурация объектного хранилища

В .env установлен S3=seaweedfs. В COMPOSE_FILE указан compose.s3-seaweedfs.yaml. Конфигурация обеспечивает запуск объектного хранилища SeaweedFS.

Проверка:
grep -E '^(S3|COMPOSE_FILE)=' .env

2. Запуск профиля ЛР3 и проверка bucket

Профиль lab3 запускает необходимые сервисы. Объекты размещаются в bucket lake. Для демонстрации используется интерфейс SeaweedFS по адресу http://localhost:9001/buckets/lake.

Проверка:
docker compose --profile lab3 ps

В интерфейсе показать префиксы raw и clean.

3. Соглашения по организации данных

Соглашения документированы в CATALOG.md.

Потоковое сырьё:
raw/stream/dt=YYYY-MM-DD/hour=HH/part-*.jsonl.gz

Историческое сырьё:
raw/history/dt=YYYY-MM-DD/candles-*.jsonl.gz

Очищенные события:
clean/event_date=YYYY-MM-DD/part-00000.parquet

Очищенные исторические свечи:
clean/history/event_date=YYYY-MM-DD/part-00000.parquet

Партиционирование по времени позволяет ограничивать перечисление объектов префиксом. Фиксированное имя результата обработки суток обеспечивает замену предыдущего объекта при повторном запуске. Объектное хранилище не использует обычное переименование файлов как файловая система.

4. Перенос закрытых файлов из сборщика

В collector/src/lake_sync.py реализована передача закрытых файлов JSONL.gz через boto3. Структура stream и history соответствует локальному расположению данных. Временные файлы в S3 не передаются. Повторная загрузка уже имеющегося объекта с тем же размером пропускается. Зависимость boto3 задана в collector/requirements.txt.

Проверка:
grep '^boto3' collector/requirements.txt
python3 -m unittest discover -s collector/src -p 'test_lake_sync.py' -v

6. Правила очистки данных MOEX ISS

Правила приведены в NOTES.md и реализованы в jobs/clean.sql. Отбираются события с source=moex и BOARDID=TQBR, корректным временем события и обязательными идентификаторами. Полностью пустые торговые снимки исключаются. Дубли по event_key устраняются с предпочтением более позднего received_at. Временные поля нормализуются в UTC.

Исторические минутные свечи имеют отдельную схему и преобразуются независимо от событий marketdata. Свечи не включаются в clean.events.

7. Очистка суток D и повторный запуск

jobs/clean.py выполняет запрос из jobs/clean.sql. Для суток D используются закрытые объекты S3, относящиеся к датам получения D и D+1. Результат сохраняется в одну партицию event_date=D, файл part-00000.parquet. Повторный расчёт использует тот же ключ объекта.

Для исторических свечей применяется jobs/clean_history.py, результат — отдельный clean.history. Эта схема разделяет два формата исходных событий.

Проверка:
head -n 12 jobs/clean.sql
python3 jobs/clean.py --all --dry-run
python3 jobs/clean_history.py --all --dry-run

Особенность исходных данных: для 23 октября не найдено сырьё получения 24 октября, для 27 октября — сырьё получения 28 октября. Поэтому повторная очистка этих суток откладывается до появления необходимых исходных файлов.

9. Аналитические запросы к Parquet непосредственно в S3

DuckDB использует httpfs и read_parquet с hive_partitioning=true. По замеру 02.11.2026 запрос без предиката прочитал 14 файлов, запрос с ограничением по event_date=2026-10-19 — 1 файл. Показатели входящего трафика HTTPFS соответственно 12.7 MiB и 3.5 KiB. Повторная проверка 03.11.2026 завершилась успешно.

Проверка:
python3 jobs/verify_clean.py --day 2026-10-19

10. Сроки хранения и ресурсная ёмкость

В CATALOG.md определено хранение raw.stream не менее 56 суток, raw.history и очищенных Parquet до завершения семестра и приёмки. Ёмкость диска, размеры данных и образы сервисов демонстрируются на работающем стенде.

Проверка:
du -sh data/* 2>/dev/null
df -h
docker system df

11. Управление сроками хранения

jobs/retention.py обращается к S3 через boto3, определяет устаревшие партиции по датам и выводит перечень объектов. Двухдневный режим dry-run выполнен без удаления данных.

Проверка:
python3 jobs/retention.py --layer clean --days 2 --dry-run

12. Обновление каталога данных

CATALOG.md содержит описания raw.stream, raw.history, parquet.events, clean.events и clean.history; для наборов указаны схема, размещение, время, партиционирование и потребители. Результаты clean.events используются таблицей lake.clean.events лабораторной работы 4.

Критерии основной приёмки

1. SeaweedFS работает; bucket lake содержит разделённые слои raw и clean.
2. Соглашения ключей и партиций записаны в CATALOG.md и соответствуют размещению объектов.
3. Очистка выполняется отдельно от сбора, ограничивается указанными сутками, повторная запись не создаёт вторую копию объекта.
4. SQL-запросы читают Parquet непосредственно из S3; предикат по партиции сокращает количество прочитанных файлов.
5. Сроки хранения определены; реализован dry-run и управляемое удаление устаревших объектов; каталог актуализирован.
6. Для приёмки предъявляется датированная точка восстановления после ЛР1 и актуальная копия сырья вне виртуальной машины.
