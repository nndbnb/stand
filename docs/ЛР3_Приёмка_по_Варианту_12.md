## Пункты задания 1–12 — демонстрация в порядке PDF

### 1. Конфигурация SeaweedFS — ✅ код стенда, ⚠️ текущая `.env` локальная

```bash
grep -E '^(S3|COMPOSE_FILE|S3_BUCKET|COLLECTOR_LAKE_PREFIX)=' .env
```

Ожидаемые принципы: `S3=seaweedfs`; среди файлов `COMPOSE_FILE` есть `compose.s3-seaweedfs.yaml`; `COLLECTOR_LAKE_PREFIX=raw`. **Говорим:** SeaweedFS обеспечивает S3-совместимый доступ к объектам, не является SQL-движком.

### 2. Запуск профиля и проверка bucket — ✅ исторически работало

```bash

```

Открыть `http://localhost:9001/buckets/lake` в браузере стенда (адрес доступен при опубликованном порте). Показать `raw/stream`, `raw/history`, `clean`. **Не заявлять**, что сервис работает сейчас, если `docker compose ps` не подтверждает.

### 3. Соглашение об именовании и партициях — ✅

```bash
grep -n -A17 '^## ЛР3' CATALOG.md
```

Объяснить раскладку:

```text
s3://lake/raw/stream/dt=YYYY-MM-DD/hour=HH/part-*.jsonl.gz
s3://lake/raw/history/dt=YYYY-MM-DD/candles-*.jsonl.gz
s3://lake/clean/event_date=YYYY-MM-DD/part-00000.parquet
```

`dt` у raw/stream — UTC-дата **получения**; `event_date` у clean — UTC-дата **события**. «Каталог» S3 — часть ключа. Переименование объекта — не обычный атомарный `mv`; замена одной и той же версии логического результата производится записью в **тот же ключ**. Полный list всего bucket дорог при большом числе объектов; выбирать `Prefix=`.

### 4. Копирование закрытых файлов сборщиком через boto3 — ✅

```bash
cat collector/requirements.txt
sed -n '1,180p' collector/src/lake_sync.py
```

Функции: `make_s3_client` создаёт S3-клиент, `iter_files` находит закрытые `*.jsonl.gz`, `object_key` строит ключ, `sync_one` проверяет `head_object` и при отсутствии вызывает `upload_file`, `scan_once` делает один проход, `run` повторяет периодически. Активные временные/WAL-файлы не копируются.

Показать тесты (не меняют реальные объекты):

```bash
# запускается в контейнере, где есть boto3/botocore
docker compose run --rm -T --no-deps \
  --entrypoint python collector /app/src/test_lake_sync.py
```

Проверяется повторное сканирование без повторной загрузки, разные raw-слои, конфликт размера, пропуск WAL. **Оговорка:** идентичный размер не доказывает идентичный checksum.

### 6. Правила очистки и найденные дефекты — ✅ правила, ⚠️ полнота отчёта о дефектах

```bash
grep -n -A55 '^## ЛР3' NOTES.md
sed -n '1,120p' jobs/clean.sql
```

Правила SQL: `source='moex'`, `BOARDID='TQBR'`, обязательные `event_key`, `event_time`, `SECID`; отбрасывание пустых торговых снимков (`LAST/BID/OFFER/QTY/VALUE` все NULL); `TRY_CAST` времени в UTC; `ROW_NUMBER() OVER (PARTITION BY event_key ORDER BY received_at DESC, _source_file DESC)` с сохранением `_rn=1`. Исторические `candles` не смешиваются с очищенными потоковыми `events`, поскольку схемы различаются. Пояснить московское время биржи vs UTC.

### 7. Очистка суток D, сырьё D и D+1, повторяемость — ✅ реализация, ⚠️ соответствие буквальной формулировке про исторический срез

```bash
python3 jobs/clean.py --day 2026-10-19 --dry-run
sed -n '1,150p' jobs/clean.py
sed -n '1,155p' jobs/clean.sql
```

В реализации `clean.py` генерирует `jobs/clean.sql`: подставляет D, D+1, входные S3-шаблоны и `s3://lake/clean/event_date=D/part-00000.parquet`; DuckDB читает S3 через `httpfs`, пишет только D. В `clean.sql` используются `COPY ... FORMAT PARQUET COMPRESSION ZSTD ROW_GROUP_SIZE 32768 OVERWRITE_OR_IGNORE TRUE`, `ROW_NUMBER()` для дедупликации. Повторный запуск заменяет тот же ключ.

**Важное расхождение с буквальным п.7 PDF:** PDF формулирует чтение «поток и исторический срез», а реализация читает **только `raw.stream`**, сознательно не объединяя несовместимые `candles` с `events`. Нужно отдельно согласовать трактовку с преподавателем; нельзя утверждать, что исторический срез обрабатывается этим запросом.

**Другая тонкость:** скрипт проверяет закрытие календарного дня, но не доказывает, что в S3 действительно есть *полный* набор файлов D+1; частичные даты возможны.

### 8. Очистка всей истории и объяснение различий в счёте — ⚠️ не до конца доказано

```bash
python3 jobs/clean.py --all --dry-run
python3 jobs/verify_clean.py --day 2026-10-19
```

Из `NOTES.md`: очищено 14 доступных UTC-партиций, 488 499 719 байт, 7 814 151 строк суммарно; контрольная дата 19.10: **724 665 строк, 724 665 уникальных ключей**. Полный повторный запуск давал то же число для контрольного дня.

**Не хватает для буквальной приёмки:** явной таблицы `число raw-событий за выбранный день D и опоздавших из D+1 → после фильтров → clean` со счётчиками отбракованных и дублей. Также в заметках зафиксирована неполнота покрытия отдельных дат; исторические candles не включены в `clean.events`. Не говорить «очищена абсолютно вся накопленная история».

### 9. Запрос непосредственно к Parquet в S3 и `EXPLAIN ANALYZE` — ✅

```bash
python3 jobs/verify_clean.py --day 2026-10-19
```

На 02.11: без условия `event_date` — **14 файлов, 247 HTTP GET, 12,7 MiB HTTPFS in, 0,201 c**; с условием на 19.10 — **1 файл, 1 GET, 3,5 KiB HTTPFS in, 0,0137 c**. Говорим «partition pruning»; это величины конкретного плана, не физический объём всех данных в Parquet.
