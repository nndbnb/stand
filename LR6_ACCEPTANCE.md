# ЛР6. Поток MOEX TQBR через Apache Kafka

Вариант 12, «Поток событий», стр. 12–13. Шесть пунктов основного задания дают 15 баллов, демонстрация перекоса — ещё 2. Предусловия по заданию — принятая ЛР5 и работающая выгрузка закрытых файлов в озеро. Время во всех командах — UTC.

## Получить ветку, сохранив локальные правки ЛР5

На стенде из предыдущей работы есть `~/stand/.env` и `~/stand/data`. Для первого запуска создай рядом каталог `~/stand-lr6`. Команды используют URL репозитория курса, поскольку на твоём стенде `origin` указывает на другой набор веток.

```bash
cd ~/stand &&
git fetch https://github.com/nndbnb/stand.git lab6 &&
git worktree add --detach ../stand-lr6 FETCH_HEAD &&
cp -p .env ../stand-lr6/.env &&
ln -s "$PWD/data" ../stand-lr6/data &&
cd ../stand-lr6
```

В новой копии свой файл настроек, а данные и Docker-проект общие с ЛР5. Все дальнейшие команды выполняй из `~/stand-lr6`. При повторном запуске достаточно перейти в этот каталог.

## Подготовить стенд один раз

Команды выполняются **в WSL**, из каталога ЛР6 с исходниками, заполненным `.env` и данными прежнего стенда. Для демонстрации роста отставания выбери время, когда сборщик MOEX получает новые события: в логах `poll` поле `kept` должно периодически быть больше нуля.

```bash
bash scripts/lr6_apply.sh
```

Скрипт сохраняет копию настроек в `.env.before-lr6`, добавляет Kafka в `COMPOSE_FILE`, собирает образ сборщика, останавливает профиль ЛР5 и поднимает ЛР6. Затем создаёт тему, регистрирует Avro v2, проверяет отказ несовместимой версии и переключает службу в `produce`. Запусти потребитель в **терминале A** и оставь его открытым:

```bash
.venv/bin/python jobs/sink.py
```

Открой **терминал B** в том же каталоге. Все команды ниже, кроме остановки и запуска потребителя, выполняются в B.

## 1. Сборщик пишет в файлы и Kafka, sink выгружает в озеро

```bash
docker compose logs --since 10m collector | grep -E '"msg":"(poll|closed|published|publish_retry)"' | tail -20
find data/raw/stream -name '*.jsonl.gz' -printf '%T@ %p\n' | sort -nr | head -3
.venv/bin/python jobs/lr6.py stats
```

Покажи время последнего закрытого файла и строку `published`: `count` — сколько событий подтвердил брокер. При активных торгах повтори `stats`: в рабочей партиции увеличивается `messages`. В A покажи строку `raw/topic/dt=…/hour=…/p…parquet  next-offset=…`: объект уже записан в S3, группа подтвердила следующее смещение. Первое закрытие файла происходит при достижении размера сегмента или смене часа.

## 2. Реестр отклоняет несовместимую схему

```bash
.venv/bin/python jobs/lr6.py registry
```

Покажи subject `moex.tqbr.events-value`, ID зарегистрированной схемы, `BACKWARD`, `is_compatible: false` и `registration_status: 409`. В [схеме v2](schemas/event_v2.avsc) поле `event_time` — long с логическим типом timestamp-millis. Проверка пробует заменить его на string. В режиме BACKWARD новый читатель должен читать данные предыдущей версии. Такой заменой это условие нарушается.

## 3. Сверить raw.stream и raw.topic

Дождись конца часа, в котором уже работали produce и sink, и выгрузки закрытых файлов. Команда находит последний завершённый час с файлами обоих наборов. Для проверки полного часа предпочтителен час, в котором сборщик работал в режиме produce с самого начала.

```bash
hour=$(.venv/bin/python jobs/lr6.py common-hour) &&
  .venv/bin/python jobs/lr6.py compare "$hour"
```

Покажи `hour`, число строк каждого набора и **два** результата DuckDB: `stream_only` и `topic_only`. Это число различных `event_key`, обнаруженных только на одной стороне. Два нуля при непустых наборах подтверждают совпадение. Если число отлично от нуля, покажи напечатанные примеры событий: сравни их время с запуском produce, логами повторной отправки и отставанием sink. Например, в час перехода на produce ранние снимки могли записаться только в файлы. Подтверди причину временем перехода или повтори сверку за следующий полный час. При разном числе строк и нулевой разности ключей проверь повторную доставку.

## 4. Повторить записанный час в отдельную тему

```bash
hour=$(.venv/bin/python jobs/lr6.py stream-hour) &&
  .venv/bin/python jobs/lr6.py replay "$hour"
```

Можно явно выбрать имеющийся час, например заменить `"$hour"` на `2026-10-12T13`, если в озере есть его файлы. Команда считает строки исходных gzip-файлов, воспроизводит час с ускорением 120× и проверяет количество по смещениям Kafka. Один запуск сразу даёт два повтора для допзадания. У каждого новая тема, поэтому старые сообщения не попадают в счётчик.

Покажи `data/lr6/replay.json`: поле `hour`, число строк `source_rows`, имя темы и три значения `messages`. Для каждого повтора их сумма должна равняться `source_rows`. Повтор можно провести на старом торговом часе даже при закрытой бирже.

## 5. Показать рост и погашение отставания

1. При работающем A выполни в B `.venv/bin/python jobs/lr6.py lag`. Найди строку активной партиции. `CURRENT-OFFSET` — подтверждённая позиция sink, `LOG-END-OFFSET` — конец журнала. Их разность — `LAG`.
2. Останови **только sink** через Ctrl+C в A. Сборщик продолжает публиковать. Выполни команду в B сразу и через 2–3 минуты. Покажи одну и ту же партицию: позиция sink стоит, конец журнала и LAG растут. Если конец журнала стоит, проверь `published` из пункта 1 и дождись новых снимков MOEX.
3. В A снова запусти `.venv/bin/python jobs/sink.py`. Повтори команду в B до `LAG = 0` у активной партиции. У пустых партиций Kafka может показывать прочерк. Все снятые таблицы с временем лежат в `data/lr6/lag.txt`.

## 6. Обосновать ключ и число партиций, показать каталог

Открой в [NOTES.md](NOTES.md) раздел «ЛР6. Поток событий» и в [CATALOG.md](CATALOG.md) раздел «ЛР6. Поток MOEX через Kafka». Покажи две строки — тему `moex.tqbr.events` и набор `raw.topic`. Объясни путь одного снимка: сборщик берёт схему из Karapace, Kafka сохраняет снимок под ключом доски, sink декодирует его по ID схемы и пишет в каталог часа получения. Три партиции позволяют назначить работу трём потребителям одной группы. На варианте с одной доской ключ `BOARDID=TQBR` задействует одну партицию.

## Допзадание. Измерить перекос и проверить исправление

Открой тот же `data/lr6/replay.json`. В `live` показана основная тема, в `runs` — два измерения на одинаковом часе. У каждой партиции `messages` — разность конца и начала журнала, `bytes` — размер журнала у брокера.

| Что показать | Как объяснить |
|---|---|
| `BOARDID`: назови номер партиции с максимальным `messages`, её число сообщений и байты. | Все записи TQBR используют один ключ. Порядок публикации сохраняется для всей доски, основная работа приходится на одного потребителя. |
| `SECID`: назови самый большой счётчик и сравни с предыдущим максимумом. | Снимки одной бумаги по-прежнему упорядочены. Разные бумаги распределяются по партициям и допускают параллельную обработку. |
| Для каждой темы раздели её максимум `messages` на `source_rows`. | Это доля самого загруженного потребителя при отдельном потребителе на партицию. Снижение доли показывает эффект. Если в часе мало различных бумаг, выбери более активный час и повтори опыт. |

Файлы для сдачи после прогона: `data/lr6/registry.json`, `compare.json`, `replay.json`, `lag.txt` в том же каталоге. При показе первого пункта открой также терминал A и логи сборщика.
